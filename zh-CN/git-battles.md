说实话，Git 给我的迎头痛击已经多到数不清。每次我以为终于理顺发布流程，它就喊一声“没那么快！”，接着两记刺拳、一记左勾拳再加上勾拳，直接把我打趴在地。我都不知道发生了什么：分支不同步、合并冲突像打地鼠一样冒出来、版本号看上去简直像彩票号码……一团糟。

不过，经历无数次修改、暂存和吃亏后的学习，我终于建立了一套能放心遵循的流程。而且我得说，能确定发布到 PyPI 和 GitHub 的代码，就是我真正想发布的代码，而不是最后一刻拼凑起来的科学怪人版本，这感觉真好。

我是这样走到这一步的。

---

# 最初的挣扎

刚开始这个项目时，我根本没有分支策略。所有开发都直接在 main 上进行。这意味着别人克隆仓库时，很可能得到一个坏掉的快照。

我是系统架构师，也真心认同 Git 及其众多功能的价值。可我就是搞不清该如何有效使用它。开始探索*分支*、*从分支再分支*、*合并*这些神奇操作后……只能说我过得不太顺利。事情常常失控，等我终于整理好，版本号已经从 0.15.0 变成了 0.15.8。

---

# 转折点

很明显，我需要一个清楚而且可重复的计划。于是我坐下来写了一份[分支策略](https://db4e.osoyalce.com/pages/Git-Branching-Strategy.html)：main 用于稳定发布，dev 用于集成，feature 分支用于新功能，release 分支用于发布前准备，bugfix 分支从 main 创建。不只是宏观说明，我还写下了需要的*每一条*命令。老实说，目前大概完善了 95%。

我不只在仓库里记录流程，还把它放进项目外部的知识库。关键原因在于：当我切换分支、更新仓库内的文档时，发布说明本身也会跟着改变。这简直像照着一张每走几步就重新绘制的地图前进。保留一份稳定的外部文档，真的拯救了我的理智。

---

# 实战经验

最让我开眼界的是那次臭名昭著的 `pyproject.toml` 版本号冲突。main 和 release 分支里各有不同的版本号，而 Git 要我选一个。我学会了迅速识别并修复这种冲突，现在只在 release 分支上提升版本号。

另外，stash 是我的好朋友。当 main 一团乱时，我把混乱先 stash 起来，完成合并，然后丢弃 stash，因为我其实不需要那些本地改动。这不算优雅，但确实救过我好几次。

---

# 胜利

终于，在完整模拟整个发布流程之后：feature 分支、合并到 dev、创建 release 分支、更新版本号、合并回 main、打标签、推送，我顺利把一切发布到 GitHub 和 PyPI，毫无意外。

最棒的一刻是创建一个全新的虚拟环境，从 PyPI 安装自己的软件包，发现它正好就是我打算发布的代码。完美！

---

# 给开发者同行的一些建议

* 从简单开始，逐步完善流程。
* 把发布检查清单保存在仓库外部，确保稳定、随时可用。
* 不要害怕合并或 stash，Git 是工具，不是暴君。
* 等手动流程真正稳固之后，再考虑自动化。

另外，学习这些步骤时，不妨请一位 Git 老手在旁边指导。

---

# 最后的想法

Git 大概还会继续揍我，但我已经不再害怕。我有了计划、流程，以及一种**确实掌握局面**的感觉。如果你也在挣扎，坚持下去吧。Git 隧道尽头确实有光，而且值得为它努力。

你也有 Git 战斗故事吗？我很想听听。
